# Zymatica 10.00 Acceptance Standard

This bundle is the code/evidence standard I would use before assigning a **10.00/10 engineering rating**. A 10.00 is not awarded merely because files exist. The live repository must prove the behavior below on a clean commit.

## A. Cross-platform engineering gate

The exact live commit must show green GitHub Actions on **Ubuntu, macOS and Windows** for:

- Rust 1.98.0 `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets --locked -- -D warnings`
- `cargo test --workspace --locked`
- `cargo build --workspace --release --locked`
- C++20 Z-SPAR tests on Linux/macOS
- Python syntax compilation and existing algorithmic proof scripts

No job may be cancelled by `fail-fast`; the workflow in this bundle sets `fail-fast: false`.

## B. Real-model evidence, not synthetic-only proofs

Commit a directory such as `evidence/10_00/latest/` containing these machine-readable files generated by `tools/ten_out_of_ten/real_model_validation.py`:

1. `hyper_kv.json`
   - at least 32 real prompts
   - reconstructed `past_key_values` actually reinjected into the same model
   - measured compression ratio >= 2.0x
   - next-step top-1 parity >= 90%
   - mean next-step KL divergence <= 0.10

2. `wormhole.json`
   - real hidden activations from two different causal LMs
   - >=100 training prompts and >=25 held-out prompts
   - learned low-rank bridge, not deterministic pseudo-random projection
   - held-out target hidden-state cosine >= 0.75
   - target LM-head top-1 agreement >= 60%

3. `epigenetic.json`
   - real model, real linear-layer update
   - >=128 calibration activation rows
   - max calibration preactivation delta <= 1e-4
   - adaptation loss improves
   - base loss degradation <= 2%
   - wording remains “nullspace-constrained update”; do not claim universal catastrophic forgetting elimination from this alone (evaluation criteria)

4. `mcts.json`
   - uses a real target LM-head/reward objective during search
   - >=16 prompts
   - objective improves on >=60% of prompts
   - median log-probability improvement > 0

Run:

```bash
python tools/ten_out_of_ten/acceptance_gate.py --evidence-dir evidence/10_00/latest
```

It must print `PASS`.

## C. Cryptographic/ZK evidence

The Groth16 suite must include negative mutation tests for every public input: identity, nullifier, attestation, ciphertext/coordinate commitment, both gateway limbs, deposit commitment and firmware hash. Mutating any bound public input after proof creation must make verification fail. Nonce mutation and malformed proof/input encodings must also fail closed.

Production FFI verification should load the expected verifying key and fail closed if it is unavailable; it should not silently generate a replacement production key.

## D. Claims and terminology

The README and research docs must distinguish:

- **implemented**
- **experimentally measured**
- **synthetic/reference test**
- **hypothesis/specification**

Claims of exceptional performance or fixed compression ratios require a committed evidence artifact and an inline evidence marker (e.g. `[EVIDENCE: evidence/10_00/latest/MANIFEST.json]`). Avoid “zk-VDE decryption” unless a VDE is actually implemented; the current relation is better described as a private coordinate/ciphertext commitment relation.

## E. Licensing/provenance

- Root Covenant license must not overwrite rights of upstream MIT/Apache components.
- Every component must have a clear provenance/license mapping (`LICENSES.md` is recommended).
- Do not bulk-relicense files unless ownership is known.
- Source files explicitly declared Zymatica-owned in `LICENSE_SCOPE.txt` must carry the Covenant SPDX identifier.
- Genuine upstream files should be placed in `THIRD_PARTY_LICENSE_ALLOWLIST.txt` and retain their original notices.

## F. Governance/release integrity

Before the final rating:

- protect `main`
- require all three matrix checks
- block force-push and deletion
- use a signed release tag (and signed commits if practical)
- run the `Zymatica 10.00 Release Evidence Gate` on the exact release commit/tag
- publish the evidence manifest and hashes

A clean GitHub-hosted run proves reproducibility in a fresh environment. A second independent machine/reviewer reproducing the same evidence is the final credibility multiplier.
